# Receipt Lineage Reconciliation

**Status:** additive reconciliation doc. References — does **not** edit —
[`docs/RECEIPT_CONTRACT.md`](../RECEIPT_CONTRACT.md) and
[`docs/specs/OPEN_DECISION_RECEIPT.md`](./OPEN_DECISION_RECEIPT.md). No schema file is
touched by this document: `aragora/gauntlet/odr_schema.json` is unmodified.

## Purpose

Per the front-door positioning in [`README.md`](../../README.md) (quoted verbatim; not
edited by this document):

> **Aragora is an auditable execution control plane for AI-assisted decisions: multi-model review in, a verifiable Decision Receipt out.**

The "receipt out" half of that sentence is not one artifact. "Decision receipt"
currently names at least three independent code lineages in this repo, each with its
own module path, its own hashing/signing mechanism, and its own level of maturity.
This document maps the three lineages, states which one is canonical for which
audience, and documents how each lineage's decision-state (`verdict`) field relates to
the others. It introduces no new receipt implementation, changes no schema, and does
not edit `RECEIPT_CONTRACT.md`.

## Canonical decision

Per [`docs/RECEIPT_CONTRACT.md`](../RECEIPT_CONTRACT.md) (quoted verbatim; not edited
by this document):

> Canonical receipt contract for new integrations: `aragora.receipts.DecisionReceipt`
> Implementation target: `aragora.gauntlet.receipt.DecisionReceipt`
> Legacy compatibility model (still used by some handlers): `aragora.export.decision_receipt.DecisionReceipt`

`RECEIPT_CONTRACT.md` speaks only to *internal* integrations. This document adds the
public-facing half of the picture that it does not itself state:

- **`aragora.gauntlet.DecisionReceipt` is the internal canonical record.** It is the
  audit-grade artifact Aragora's own CLI, server, and handlers create, store, and
  query. It is not designed to be read outside a running Aragora instance.
- **The Open Decision Receipt (ODR v0.1) is the canonical PUBLIC artifact.** It is the
  portable, vendor-neutral export format
  ([`docs/specs/OPEN_DECISION_RECEIPT.md`](./OPEN_DECISION_RECEIPT.md)) meant to travel
  outside Aragora and be checked by a third party with no Aragora installation, using
  only the published schema and, optionally, a public key.

These are complementary, not competing: every ODR document is *derived from* a native
`DecisionReceipt` via the reference emitter
(`aragora/gauntlet/odr_export.py::decision_receipt_to_odr`); nothing produces an ODR
from scratch.

## The three lineages

| Lineage | Module path(s) | Hashing / signing | Maturity |
|---|---|---|---|
| **① Internal canonical** — native `DecisionReceipt` | `aragora/gauntlet/receipt_models.py` (dataclass `DecisionReceipt`, `schema_version = "1.1"`); builders/exporters in `aragora/gauntlet/receipt.py`; re-exported as `aragora.receipts.DecisionReceipt` (`aragora/receipts/__init__.py`) | `artifact_hash` = SHA-256 hex over a 6-field subset (`receipt_id, gauntlet_id, input_hash, risk_summary, verdict, confidence`) via `json.dumps(..., sort_keys=True)` — deterministic, but not JCS. Signing is opt-in via `.sign()` → `aragora/gauntlet/signing.py::ReceiptSigner` (default backend **HMAC-SHA256**, key from `ARAGORA_RECEIPT_SIGNING_KEY` / a durable file key / an ephemeral key; RSA-SHA256 and Ed25519 backends also exist and are selectable by constructing that backend explicitly). | Production; widely used across CLI/server/handlers. A documentation schema exists (`docs/schemas/gauntlet_receipt.v1.json`, generated by `scripts/generate_receipt_schema.py`) but is **not loaded or validated at runtime** — no code path calls `jsonschema.validate` against it. `RECEIPT_CONTRACT.md` names this lineage canonical for new *internal* integrations. |
| **② Public canonical** — Open Decision Receipt (ODR v0.1) | Spec: `docs/specs/OPEN_DECISION_RECEIPT.md`; schema: `aragora/gauntlet/odr_schema.json` (JSON Schema draft 2020-12); reference emitter: `aragora/gauntlet/odr_export.py` (`decision_receipt_to_odr`, `jcs_canonicalize`, `odr_content_digest`); detached signing: `aragora/gauntlet/odr_signing.py` (`generate_signing_key`, `sign_odr_receipt`, `public_key_pem`); **in-tree verification engine `aragora/gauntlet/odr_verify.py`** (`verify_odr_document`, landed 2026-07-02 via #8389, parallel to the standalone `aragora-verify` package — see "Two verifiers" below). | `odr_digest` = `SHA-256(JCS(doc − "signatures"))` per RFC 8785; optional detached **Ed25519** signature(s) in `signatures[]`, produced by `odr_signing.py` (production key custody via AWS Secrets Manager) and checked by either verifier below. | Draft v0.1 (issues #8223–#8225), Tier 2. Schema conformance *is* enforced in at least one production path: `scripts/emit_pr_receipt.py --verify` calls `jsonschema.validate(odr, load_odr_schema())` directly. `odr_verify.py` is a second, dependency-light conformance path — not yet wired to a shipped CLI/HTTP entry point of its own (detail below). |
| **③ Legacy / adapter** | `aragora/export/decision_receipt.py` (dataclass `DecisionReceipt`, `schema_version = "1.0"`; re-exported as `aragora.receipts.LegacyDecisionReceipt`) **and** `aragora-debate/src/aragora_debate/receipt.py` + `types.py` (`ReceiptBuilder`, its own `Verdict` enum) | `export.decision_receipt`: `checksum` = SHA-256 hex **truncated to 16 chars**, over a 7-field subset (`receipt_id, verdict, confidence, findings_count, critical_count, timestamp, audit_trail_id`); signing via the same `signing.py::ReceiptSigner`, hardcoded to the HMAC backend. `aragora-debate`: default signature is a plain **SHA-256 content hash** (`signature_algorithm = "SHA-256-content-hash"`) over the payload with signature fields excluded; `ReceiptBuilder.sign_hmac()` optionally upgrades to **HMAC-SHA256** with a caller-supplied key. | `RECEIPT_CONTRACT.md` names `aragora.export.decision_receipt.DecisionReceipt` explicitly as the **legacy compatibility model, still used by some handlers** (e.g. `GET`/`POST /receipts/{id}/verify` in `aragora/server/fastapi/routes/receipts.py`). Neither module in this lineage canonicalizes with JCS or signs with Ed25519, so **neither is verifiable by `aragora-verify`** — they predate the ODR profile and are not themselves on a path to become ODR-compatible (only via export from lineage ①). |

### Two verifiers for the public lineage, and how they relate

The public (ODR) lineage has **two independent verification implementations** that
must be kept in lockstep:

1. **`aragora/gauntlet/odr_verify.py`** — the in-tree engine landed via #8389. Its module
   docstring previously overclaimed itself as "the server-side single implementation
   that the `POST /api/receipts/verify` endpoint and any internal caller wrap"; that
   wording has been corrected because no shipped CLI subcommand or HTTP route actually
   imports `verify_odr_document` / `odr_verify` — the existing
   `/api/v2/receipts/{id}/verify*` routes and `/receipts/{id}/verify` verify the
   **native or legacy** receipt instead (`store.verify_signature`/`verify_integrity`, or
   `aragora.export.decision_receipt.DecisionReceipt.verify_integrity`), not an ODR
   document. The docstring now states this accurately: an in-tree **library** engine,
   kept in lockstep with the standalone `aragora-verify` package, not yet wired to any
   shipped CLI/HTTP entry point. `odr_verify.py` is exercised today by its own test
   suite (`tests/gauntlet/test_odr_verify.py`, `tests/gauntlet/test_odr_verify_schema.py`)
   and is available for internal callers to import directly.
2. **`aragora-verify`** (this repo's standalone `aragora-verify/` package, **published
   on PyPI**) — the "no-trust" path: pure stdlib + `cryptography`, zero Aragora
   dependency, with its own real CLI entry point
   (`aragora-verify RECEIPT.odr.json [--pubkey KEY.pem] [--chain CHAIN.jsonl]`) for an
   external auditor who has never installed Aragora. `aragora-verify` is live on
   PyPI; 0.2.0 (2026-09-25) is the latest published version, and 0.1.0 was first
   published 2026-06-29T23:32Z (GitHub release
   [`aragora-verify-v0.1.0`](https://github.com/synaptent/aragora/releases/tag/aragora-verify-v0.1.0)).
   Use `pip install "aragora-verify>=0.2.0"` for the public-index verifier today:
   0.2.0 is the first line that verifies ODR v0.2, the default export format from
   release 2.11.0, and it keeps 0.1.1's signer `key_id` binding that 0.1.0 lacks.
   Self-verify rather than trust this sentence: `python3 -m pip index versions
   aragora-verify` or `curl -s https://pypi.org/pypi/aragora-verify/json`. To
   exercise this exact checkout instead of the published package, run
   `PYTHONPATH=src python -m aragora_verify <r>.odr.json` from `aragora-verify/`, or
   `pip install ./aragora-verify` for a local `aragora-verify` console script. Its
   exit-code contract is `0 verified / 1 failed / 2 usage / 3
   signatures-present-unchecked`.

Both engines are hand-rolled, dependency-light mirrors of the same normative artifact
— `aragora/gauntlet/odr_schema.json`, also bundled inside the `aragora-verify` package
at `aragora-verify/src/aragora_verify/odr_schema.json` — and both implement the same
digest and signature construction
(`aragora.gauntlet.odr_export.odr_content_digest`; ODR spec §6, issue #8225).
`odr_verify.py`'s own comments warn: "Keep the two in lockstep — a schema change
without a matching change here reopens the #8765 bypass class."
`tests/gauntlet/test_odr_signing.py` round-trips a receipt signed by the in-tree
`odr_signing.py` through the *shipped* `aragora_verify` package specifically to prove
the two are interoperable, not merely similarly named.

Do not confuse either ODR verifier with `aragora verify <file>` /
`aragora receipt verify <file>`, which validate the **native gauntlet** receipt
(lineage ①) — a different object, with a different schema, than an ODR document.

## Decision-state (verdict) mapping

`claim.verdict` in the ODR v0.1 schema (`aragora/gauntlet/odr_schema.json`) is declared
as:

```json
"verdict": {
  "type": "string",
  "minLength": 1,
  "description": "Outcome asserted about the subject (e.g. PASS / CONDITIONAL / FAIL)."
}
```

**There is no enum.** `claim.verdict` is an **emitter-specific free string** — any ODR
emitter, Aragora's or a third party's, may write any non-empty string there, and no
schema change is needed (nor made by this document) to add new values. This is
deliberate and tracked as a known gap (`architecture.md` gap G3): the ODR profile does
not standardize a closed decision-state vocabulary in v0.1.

Contrast this with the *internal* documentation schema for lineage ①,
`docs/schemas/gauntlet_receipt.v1.json`, which **does** define an enum:

```json
"verdict": {
  "type": "string",
  "description": "Final verdict. Gauntlet uses PASS/CONDITIONAL/FAIL; maps to aragora.core_types.Verdict values.",
  "enum": ["PASS", "CONDITIONAL", "FAIL", "approved", "approved_with_conditions", "needs_review", "rejected"]
}
```

That enum is not runtime-enforced either (see the lineage table above), and it is
already incomplete relative to what ships: the merge-quorum wedge
(`aragora/swarm/quorum_receipt.py:58`, `verdict = "PASS" if reached else
"CHANGES_REQUESTED"`) writes `CHANGES_REQUESTED` into that same native
`DecisionReceipt.verdict` field, and `CHANGES_REQUESTED` is not in the enum above. In
practice `verdict` is a free string end-to-end — formally in ODR, and informally
(enum notwithstanding) in the native record too.

### Reading-aid crosswalk (non-normative)

For readers translating between a PASS/CONDITIONAL/FAIL mental model and an
approval-workflow mental model, this document defines the following crosswalk. It is
**not** enforced by any schema or code enum — it exists only to aid human and
downstream-consumer interpretation of `claim.verdict` strings, and adds no constraint
to the schema:

| Gauntlet-style | Approval-style |
|---|---|
| `PASS` | `approved` |
| `CONDITIONAL` | `conditional` |
| `FAIL` | `blocked` |

### Abstained / inconclusive handling

The ODR v0.1 profile has no dedicated "abstained" or "inconclusive" verdict, and no
shipped Aragora emitter currently produces one. The authoritative signal for "no
decision reached" is `quorum.reached: false` (a required boolean in the `quorum`
present-block) — not `claim.verdict` — precisely because `claim.verdict` is a free
string and a consumer cannot rely on its literal text alone to detect non-decision.
Today, even when `quorum.reached` is `false`, the merge-quorum emitter still assigns a
substantive verdict string (`CHANGES_REQUESTED`) rather than writing `"ABSTAINED"` or
`"INCONCLUSIVE"`.

Because `claim.verdict` accepts any non-empty string, an emitter that wants to
represent an explicit abstention or an inconclusive outcome may write `"ABSTAINED"` or
`"INCONCLUSIVE"` (or any other domain-appropriate string) today, with no schema
change required — but it should pair that string with `quorum.reached: false` so
automated consumers do not have to pattern-match on verdict text to detect
non-decision. Per-participant abstention (an individual agent declining to vote) is a
distinct, narrower concept tracked elsewhere in the codebase (e.g. `JudgeVote.ABSTAIN`
in `aragora/debate/judge_selector.py`) and is **not** represented in the ODR
`quorum.participants[]` shape, which records only `agent`, `model_family`, and
`model_id` per participant. That gap is noted here, not closed by this document.

### Verdict strings observed in shipped fixtures

| Verdict string | Source | Meaning |
|---|---|---|
| `PASS` | `docs/specs/examples/example-decision-receipt.odr.json` | Gauntlet-style pass, from the reference emitter |
| `CHANGES_REQUESTED` | `docs/specs/examples/example-merge-quorum-receipt.odr.json`; emitted by `aragora/swarm/quorum_receipt.py` when quorum is not reached | Approval-workflow-style verdict from the merge-quorum wedge — outside both the crosswalk above and the (non-enforced) native enum, which is exactly the point: `claim.verdict` is free text in practice, not only in the schema |
| `UNKNOWN` | `aragora/gauntlet/odr_export.py:223`, `claim = {"verdict": receipt.verdict or "UNKNOWN"}` | Fallback the reference emitter writes when the source native `DecisionReceipt.verdict` is empty/falsy; `claim.verdict` is a required non-empty string, so the emitter never omits it |

No changes were made to `aragora/gauntlet/odr_schema.json` to produce this document;
all three verdict strings above already validate against the existing, unmodified
schema, because `claim.verdict` has always accepted any non-empty string.
